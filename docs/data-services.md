# Data services

A cluster can run a PostgreSQL and a Redis that its functions reach without any
connection string to manage. The platform starts the container, generates the
password, injects the connection into every isolate, and gives you a browser for
the contents.

These are for the functions running on this instance. They are not a managed
database product: there is no automatic backup, no failover and no read replica.

## Creating one

From the console, under Data services. Or:

```bash
cubicle services create postgres
```

| Kind | Versions | Default |
| --- | --- | --- |
| `postgres` | 16.3, 15.6, 14.11 | 16.3 |
| `redis` | 7.2, 7.0, 6.2 | 7.2 |

Memory is allocated from the cluster's ceiling like anything else, so creating
one can be refused if the cluster is already committed.

## Using one from a function

Both are already connected. Nothing is imported by URL and no password appears
in your code:

```python
from cubicle_db import postgres, redis

def handler(req, ctx):
    if postgres.available:
        with postgres.session() as db:
            rows = db.execute("select id, amount from orders where actor = :a", a="me")

    if redis.available:
        redis.setex("last-seen", 300, req.session_id)
```

`.available` is false when the service does not exist or is stopped, so a
handler can be written to work either way rather than crashing when someone
stops the database.

Queries take bound parameters. Build a query by concatenation and you have
written an injection into your own function; the platform cannot prevent that
for you.

## Browsing the data

The console has a table browser for Postgres and a key browser for Redis, both
under Data services. They are admin only.

The table browser lists tables with row estimates and sizes, pages through rows,
sorts, searches across all columns at once, and edits rows on tables that have a
primary key. Identifiers are quoted and values are bound, so a table named
oddly is handled rather than exploited.

There is also a query console that runs arbitrary SQL, including DDL. That is
deliberate: it is the operator's own database, and a browser that cannot run
DDL is a toy. The guards are the admin role, a fifteen second statement timeout
and a five hundred row cap on results. Anyone who can reach it can drop your
tables, so keep the admin role narrow.

The Redis browser lists keys by pattern, shows values by type, and runs
commands.

## Connections and passwords

```bash
cubicle services url postgres
```

The URL contains the password, which is why it is printed only by that command
and never in the service list.

Passwords are generated by the platform and stored encrypted. They are not
rotated automatically; recreating the service generates a new one.

## Lifecycle

| Command | Effect |
| --- | --- |
| `cubicle services stop <kind>` | Stops the container. Data survives. `.available` becomes false |
| `cubicle services start <kind>` | Starts it again |
| `cubicle services recreate <kind>` | Destroys and rebuilds the container. **The data is gone** |
| `cubicle services rm <kind>` | Removes the service entirely |

Recreate exists for a container that is broken rather than a database that is
wrong. It confirms hard, and `--yes` is the only way past it.

## Backups

There are none. If the data matters, take your own:

```bash
docker exec <container> pg_dump -U cubicle cubicle > backup.sql
```

`cubicle services show postgres` prints the container name. Put that on a timer
outside Cubicle. A function on a schedule is not a good place for it, because
the backup should survive the platform being down.
